# ai-build-council 要件定義

Version: 1.0.0（ai-council_v2の会合により策定、裁定：条件付き承認）

---

# 1. 目的・背景

ai-build-councilは、ai-council_v2の姉妹ツールとして、実際にコードを設計・
実装・テスト・レビューし、成果物を記録するClaude Codeスキルである。

ai-council_v2は「議論と意思決定」だけを担当し、実際のコードは書かない。
ai-build-councilはai-council_v2（またはユーザー）が作成した成果物を
**参考情報として受け取り、独自に設計・レビュー・実装を行う**。
ai-council_v2の成果物をそのまま採用することは目的としない。

両ツールは完全に独立しており、コード上の結合は一切ない（`--context-file`
相当のファイル経由の任意連携のみ許容し、ai-build-councilがai-council_v2を
プログラム的に呼び出すラッパーにはしない）。

---

# 2. スコープ

## 2.1 ai-build-councilの機能として扱う範囲

* Intake（要求の隔離・分類）→独立設計→設計査読・凍結→実装→テスト→
  実装レビュー→修正→記録、という多段階ゲート付きワークフロー
* テストの実行結果による客観的な検証（自己申告に頼らない）
* commit・push・GitHub issue/PR作成（いずれも事前承認ゲートあり）

## 2.2 ai-build-councilの機能として扱わない範囲

* 議論・意思決定そのもの（ai-council_v2の役割。ai-build-councilは
  ai-council_v2の出力を鵜呑みにせず、自身の設計フェーズで再構築する）
* Claude Agent SDK等、別プロセスによる自律実装（実装は議長Fable本体
  セッションが直接行う）
* Gemini・Grokの利用（Geminiは全面除外。Grokはai-council_v2同様、
  将来の任意拡張の余地は残すが初版では扱わない）

---

# 3. 用語定義

| 用語 | 意味 |
|---|---|
| 議長Fable | 実装を直接行い、レビュー結果を実行に落とし込む担当（Claude Code本体セッション） |
| 提案（Codex） | 設計提案・実装レビューを担当するGPT（Codex CLI） |
| 査読（Claude） | 設計査読・実装レビューを担当するClaudeサブエージェント（isolated context） |
| user_requirements | ユーザーが直接指定した拘束要件 |
| reference_proposals | ai-council_v2等、非拘束の参考提案 |
| verified_repo_facts | 実リポジトリ・ツール・実行結果から確認した事実 |
| 固定diff | 実装完了時に`git diff`で内容を凍結したもの。レビュー中に変化したら失効 |
| Test Gate A/B | 実装直後／実装レビュー後修正後の2つのテスト検証ポイント |

---

# 4. 機能要件

## 4.1 Stage 0: Intake・隔離・予算設定

* 入力を`user_requirements`（拘束要件）／`reference_proposals`
  （ai-council_v2等の非拘束提案）／`verified_repo_facts`（確認済み事実）
  の3分類に整理する
* `reference_proposals`の採用は`accepted`/`modified`/`rejected`/`deferred`
  ＋理由を必須とする（鵜呑みを防ぐ）
* 対象、禁止操作、成果物、テスト範囲、試行上限、時間・コスト上限、
  外部公開操作の可否をこの段階で確定する

## 4.2 Stage 1: 独立設計

* 提案席（Codex CLI、新規セッション、`--sandbox read-only`）が、要件・
  受入条件・テスト戦略・E2Eハーネスの要否を含む設計を作成する
* 実ブラウザAPI依存案件（Chrome拡張等）では、コア実装とテストハーネス
  構築の見積もりを分離して提示する

## 4.3 Stage 2: 設計査読・凍結

* 査読席（Claude、isolated context）が設計を批判的に査読する
* ラウンド上限：最大2ラウンド
* 不明点を解消し、要件と受入条件を固定する。凍結後の変更には記録と
  承認を要求する

## 4.4 Stage 3: 実装（議長Fable本体）

* 凍結設計に基づき、議長Fable本体セッションが直接ファイル編集・
  bash実行を行う（別プロセスは使わない）
* `--sandbox workspace-write`は議長Fable本体にのみ許可し、設計・
  レビュー席には与えない
* 実装中に設計上の問題を発見した場合、黙って逸脱せずStage 2（再承認）
  へ戻る

## 4.5 Stage 4: Test Gate A

* 単体・統合・必要なE2Eテストを実行し、生ログを保存する
  （パイプ使用時は`set -o pipefail`必須）
* 内部サブループ上限：デフォルト5回（事前に人間が変更可、実行中に
  エージェント自身が引き上げることは禁止）
* 早期停止条件：同一原因が3回連続 ／ 環境障害が2回連続 ／ ゲート内
  試行が上限到達 ／ テストの削除・緩和なしには通せない ／ 予算超過
* 「同一原因」の判定基準：失敗テスト名＋トップスタックフレームの一致、
  またはエラー型＋アサーション内容の一致。判定根拠をログに残す
* テストの削除・緩和は「設計変更」として扱い、人間の承認を必須とする

## 4.6 Stage 5: 固定diffの独立実装レビュー

* 実装完了時に`git diff`の内容をハッシュ付きで固定する。レビュー中に
  対象ファイルが変化した場合、そのレビューは失効する
* レビュー席：提案（Codex CLI、**Stage1とは別の新規セッション**、
  `--sandbox read-only`）＋査読（Claude、isolated context、実装時の
  会話は見せない）の両方が必須
* 評価軸の優先順位：(1)機能的正しさ・要求充足 (2)安全性・セキュリティ・
  データ損失リスク (3)エラー処理・競合・境界条件 (4)テストの妥当性・
  不足 (5)保守性 (6)凍結済み設計との差異。設計との差異それ自体は
  欠陥として扱わない
* 実装者（議長Fable）の説明・思考過程は、原則としてレビュワーに事前に
  見せない（アンカリング回避）
* テストコードの変更は本体コードの変更と分離してレビューする

## 4.7 Stage 6: 指摘処理・Test Gate B

* 各指摘を`Fixed`／`WontFix`／`Disputed`の3値で追跡する
* blocker/major：修正必須。議長Fable単独では`WontFix`を確定できない
  （人間の明示承認が必要）
* minor：修正または理由付き却下を議長Fable単独で判断可。却下理由は
  全件ログに残し、Stage 8で人間が事後確認できるようにする
* 意見対立（Disputed）：同一論点で最大3ラウンド
  （第1:独立意見、第2:相手の根拠を見た反論、第3:議長裁定案への異議）。
  未解決なら実装を止め、人間に選択肢・影響を提示する
* 修正後、関連テストだけでなく必要な回帰テストもTest Gate Bで実施する

## 4.8 Codex CLI呼び出しの堅牢性（全ステージ横断）

* すべての`codex exec`呼び出しは非対話モード・stdinを`/dev/null`で
  クローズ・プロセス単位のタイムアウト（デフォルト10分）を設定する
* 一定時間（目安3分）出力・CPU・対象ファイルの変化がなければハング
  候補と判定し、プロセスツリーをkillして1回だけ再実行する。再発時は
  エスカレーションし、無制限リトライはしない
* 実行ごとに終了コード・経過時間・タイムアウト有無・再試行理由を記録する

## 4.9 Stage 7: 成果確定・commit・push・記録

* commitは対象ファイルを明示指定する（`git add .`は禁止）
* push・GitHub issue/PR作成は、デフォルトOFF・対象リポジトリを明示
  パラメータで指定・実行前に人間の明示承認を必須とする（push同等の
  ゲートをIssue/PRにも適用する）
* 承認がない場合は、ローカルの実行記録・投稿用ドラフト生成までに留める
* 記録内容：commit SHA、テストコマンド・結果、未解決事項、試行回数、
  設計差分
* 人間へのエスカレーション時は、議長による要約でなく、レビュワーの
  生コメント・生ログ・diff・未解決論点リストをそのまま提示する
  （4点セット）

# 5. 非機能要件

## 5.1 独立性・監査可能性

* 実装者はレビュー指摘を消去・非表示にできない
* CLI実行ごとに終了コード・経過時間・タイムアウト・再試行理由を記録する
* 機密情報（`.env`、認証情報等）をログ・issue・レビュー入力へ含めない

## 5.2 セキュリティ

* 設計・レビュー席には`--sandbox workspace-write`を与えない
  （編集権限は議長Fable本体のみ）
* 外部公開操作（push・Issue/PR）は明示ゲート後のみ実行する

## 5.3 コスト管理

* ai-council_v2と同様、Claude・GPTはサブスクリプション運用を前提とし、
  API従量課金は発生しない設計とする
* 各ゲートに試行回数・時間・コストの上限を設け、超過時は完了未達でも
  人間に状況報告し継続可否を判断させる

---

# 6. 制約条件

* Geminiは議席・レビューから全面的に除外する
* 実装は議長Fable本体セッションが直接行う。Claude Agent SDK等の
  別プロセスは使わない
* ai-council_v2とはコード上の結合を一切持たない

---

# 7. ai-council_v2との関係

ai-build-councilはai-council_v2から完全に独立したツールである。
ai-council_v2の成果物（要件定義・稟議書等）を`reference_proposals`
として参考にすることはあるが、そのまま採用することは目的としない。
Stage 0で必ず`accepted`/`modified`/`rejected`/`deferred`の判定を経る。

# 8. このドキュメントの位置づけ

本ドキュメントは、ai-council_v2の会合（議長Fable・提案GPT・査読Claude）
により、Chrome拡張機能「音声タブコントローラー」を具体例として検証した
うえで策定したものである。裁定は「条件付き承認」（詳細は
[稟議書_ai-build-council.md](稟議書_ai-build-council.md)参照）。
人間のレビュー・承認を経てから、ai-build-councilリポジトリへの実装に
進むこと。
