# 稟議書：ai-build-council（実装特化スキル）の要件定義・設計

## テーマ

ai-council_v2の姉妹ツール「ai-build-council」（設計→実装→テスト→レビュー→記録を
行うClaude Codeスキル）の要件定義・設計を確定する。具体例としてChrome拡張機能
「音声タブコントローラー」を実際に作る場合を検証しながら検討した。

## 検討体制

| 席 | 担当 | モデル |
|---|---|---|
| 議長 | 統合・裁定 | Claude Fable（Claude Code本体セッション） |
| 提案 | 実現案・具体策 | GPT（Codex CLI, gpt-5.6-sol） |
| 査読 | 批判的検証 | Claude（Agentサブエージェント） |

## 論点整理

- 目的：ai-build-councilの要件定義・設計を確定すること
- 制約：ai-council_v2とは完全に独立（コード結合なし、内部から呼び出すラッパーに
  しない）／Geminiを議席・レビューから除外／実装は議長Fable本体セッションが
  直接ファイル編集・bash実行で行う（Claude Agent SDK等の別プロセスは使わない）／
  テストは実行結果で必ず検証する（自己申告に頼らない）
- 判定基準：ワークフローが実際に機能するか、自己レビュー回避の原則が守られて
  いるか、堅牢性（バグは通るまで修正、意見の相違はラウンド上限で人間に委ねる）

## 合意点

- ai-council_v2の出力は「参考資料」であり「仕様」ではない。採用可否は
  accepted/modified/rejected/deferred＋理由で必ず判定し、鵜呑みにしない
- 設計→設計査読・凍結→実装→テスト→実装レビュー→修正→記録、という
  多段階ゲート構造にすること
- テスト・修正ループには明示的な上限と早期停止条件が必要（無制限はNG）
- 実装完了時のdiffをハッシュ固定し、レビュー中に変化したら失効させる
  （固定diffレビュー）
- push・GitHub issue/PR作成のような外部公開操作は、デフォルトOFF・事前の
  明示的な人間の承認が必須
- `git add .`は禁止し、対象ファイルを明示指定する
- Chrome拡張のような実ブラウザAPI依存の案件では、モックテストだけでなく
  実ブラウザでのE2E検証が必要

## 相違点・議長が裁定した点

### 1. GPTの二重役割（設計提案者と実装レビュワーが同一）

**査読席の指摘**：GPTが設計も実装レビューも担当すると、自分の設計への
準拠性に評価が偏り、コード自体の正しさの評価が甘くなるリスクがある。
Stage2でも「未解消」と判定された。

**提案席の回答**：評価軸を「設計準拠」でなく「正しさ・堅牢性・セキュリティ」
中心に再定義することで軽減を図った。

**裁定**：設計（Stage1）と実装レビュー（Stage5）のCodex CLI呼び出しを
**必ず別の新規セッション**とする（対話継続・要約引き継ぎ禁止）ことを条件に
加える。同一プロバイダである以上、完全な独立性の保証はできない（両席とも
認める限界）が、セッション分離によりアンカリング効果を構造的に低減できる。
第3ベンダーによる完全独立は、Gemini除外・Grok任意（従量課金）という
既存方針とのバランスで見送る。

### 2. Codex CLIハングへの根本対策

**査読席の指摘**：「環境障害2回連続でエスカレーション」は反応的な検知に
過ぎず、ハングは「失敗」ではなく「応答なしで停止」なので、そもそも
検知条件に到達しない可能性がある（実際に今回の運用で48分間無応答の
まま停止した事例がある）。

**裁定**：全てのCodex CLI呼び出しに、非対話モード・stdin `/dev/null`
クローズ・プロセス単位のタイムアウト（デフォルト10分）・無応答時の
kill+1回リトライ+エスカレーションを標準仕様として明記する。

### 3. 「同一原因」判定基準の未定義

**裁定**：失敗テスト名＋トップスタックフレームの一致、またはエラー型＋
アサーション内容の一致、という運用定義を採用する。判定根拠は必ずログに
残し、後から人間が監査できるようにする。

### 4. minor指摘の却下権限

**裁定**：Fable単独での却下を認める（blocker/majorのような人間承認は
不要）。ただし却下理由は全件ログに残し、Stage8の記録で人間が事後確認
できるようにする。これにより運用速度を落とさず、監査可能性を確保する。

### 5. push・Issue/PR記録のゲート統一

**裁定**：push同様、GitHub issue/PR作成にも同等の事前承認ゲートを適用し、
対象リポジトリは暗黙のカレントディレクトリではなく明示パラメータとする。

### 6. テストハーネス構築の見積もり

**裁定**：Chrome拡張のような実ブラウザAPI依存案件では、コア実装と
テストハーネス構築（モック環境・E2E環境の整備）の見積もりを分離して
提示することを標準ルールとする。

## リスク（引き続き残る限界として明記）

- Codex CLIの設計・レビューが同一プロバイダである以上、セッション分離
  だけでは提供元レベルの完全な独立性は担保できない
- Codex CLIのコマンドラインオプションは将来変更されうる。導入時に
  `codex --version`・`codex exec --help`・`codex review --help`を
  preflightで確認し、未知の版では停止する設計とする
- Chromeの実E2Eは、Chromiumと配布版Chrome、headlessとheadfulで挙動差が
  出る可能性がある

## 裁定：条件付き承認

以下の条件を満たした要件定義・設計書（本ディレクトリの
`要件定義_ai-build-council.md`・`設計書_ai-build-council.md`）を承認する。

1. 設計と実装レビューのCodex CLI呼び出しは別の新規セッションとする
2. Codex CLI呼び出し全般にタイムアウト・kill・1回リトライ・
   エスカレーションを標準仕様として実装する
3. 「同一原因」判定はログに根拠を残す運用定義を用いる
4. push・Issue/PR作成は同等の事前承認ゲートとし、対象リポジトリを
   明示パラメータにする
5. minor却下は人間承認不要だが、理由を全件ログに残す
6. 実ブラウザAPI依存案件は、コア実装とテストハーネス構築の見積もりを
   分離して提示する
