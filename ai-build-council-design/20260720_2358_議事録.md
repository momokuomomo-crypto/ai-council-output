日時：2026-07-20
検討体制：議長 Claude Fable／提案 GPT（Codex CLI, gpt-5.6-sol）／査読 Claude（サブエージェント）

---

## Stage 0: 論点整理（議長）

- 検討の目的：ai-build-councilの要件定義・設計を確定すること
- 制約：ai-council_v2とは完全に独立（コード結合なし、内部から呼び出す
  ラッパーにしない）／Geminiを議席・レビューから除外／実装は議長Fable

- 具体例：Chrome拡張機能「音声タブコントローラー」を実際に作るとしたら
  ワークフローがどう機能するかを検証する

## Stage 1: 独立意見

### 提案席（GPT）の意見

## 要約

ai-build-councilは「複数AIが順番に相談するスキル」ではなく、議長Fableが
直接実装する工程を、独立設計・独立査読・実テスト・証跡で制御する
ステートマシンとして設計すべき。中核要件は次の5点。

1. ai-council_v2の出力は「参考資料」に隔離し、要求・設計・採否判断を
   再構築する。
2. 設計者、実装者、実装レビュアーの役割と入力を分離する。
3. レビューは文章ではなく、固定したGit差分とテスト証跡を対象にする。
4. バグはテスト成功まで直すが、設計意見の対立は最大3ラウンドで人間に
   戻す。
5. commit・push・Issue/PR更新は、品質ゲート通過後にのみ実行する。

Chrome拡張の例にも適用可能だが、「実装直後とレビュー後の2回テスト」だけ
では不十分。静的・単体テストに加え、実Chromeでの拡張ロード、音声再生、
タブミュート、再起動後の常時ミュート復元までを実行証跡として残す必要が
ある。

## 立場（結論）

採用すべき構成は以下の7ステージ。

```text
0. Intake / 隔離
1. 独立設計
2. 設計査読・設計凍結
3. Fable本体による直接実装
4. Test Gate A
5. 固定diffの独立実装レビュー
6. 修正・Test Gate B
7. commit / push / Issue・PR記録
```

たたき台は妥当だが、現状のままでは「設計」と「参考資料の要約」が混ざる、
何をもって独立レビューとするか、レビュー中にdiffが変化した場合の扱い、
テスト失敗と設計対立の停止条件、Chrome APIをmockしたテストと実Chrome
検証の区別、commit・pushの許可境界、作業途中で既存変更を巻き込まない
方法、が曖昧。自由形式の会議ではなく、成果物・終了条件・状態遷移を
SKILL.mdで強制する設計を推す。

## 根拠

**1. ai-council_v2の出力は入力資料であって仕様ではない**：
`user_requirements`（拘束要件）／`reference_proposals`（非拘束提案）／
`verified_repo_facts`（確認済み事実）の3分類を作る。採用には
`accepted/modified/rejected/deferred`＋理由を必須とする。

**2. 自己レビュー回避はモデル名ではなく来歴で判定する**：
レビュー担当者について`actor_id`／`role`／`authored_design`／
`edited_code`／`saw_other_reviews_before_submission`／`input_diff_sha256`
を記録する。同じClaude系でも、コードを書いておらず他レビューを見ず
固定diffだけを査読するサブエージェントなら独立査読者として扱える。
Fable本体によるセルフチェックは有用だが独立レビューの票には数えない。

**3. レビュー対象を固定しないと判定が壊れる**：実装完了時に
`git diff --binary --no-ext-diff HEAD > input.patch`等でハッシュを固定し、
全レビュアーに同じファイルを渡す。レビュー中にファイルが変わったら
そのレビューは失効。

**4. Codexは読み取り専用の非対話実行に限定する**：
`codex exec --sandbox read-only --ephemeral --output-schema ... -o ...`。
設計・レビュー席には`--sandbox workspace-write`を与えず、コード編集は
Fable本体だけが直接行うという制約を権限で守る。

**5. 「テストが通るまで」と「永遠に直す」を区別する**：テスト失敗は
原因分類→修正→再テストのループとし、上限は設けないが「同一原因3回
連続」「環境障害2回連続」「要求変更が必要」なら人間へエスカレーション。
レビュー指摘はblocker/major（修正必須）、minor（修正or理由付き却下）、
suggestion（非拘束）に分類。意見対立は同一論点で最大3ラウンド
（第1:独立意見、第2:反論、第3:議長裁定案への異議）、未解決なら人間に
選択肢・影響を提示。

## 主要な論点

必須機能要件：ユーザー要求・参考資料・リポジトリ事実の分離／Codexに
よる独立設計／Claude査読サブエージェントによる設計査読／Fable本体のみが
編集・bash実行／実装直後とレビュー修正後の実テスト／CodexとClaude査読が
同一diffを独立評価／指摘の重複排除と正規化／未解決事項を人間に返す／
全成果物にrun ID・時刻・commit・diff hashを付ける。

非機能要件：途中再開可能／同一ステージ再実行で既存証跡を上書きしない／
外部AI失敗時に「レビュー済み」と誤認しない／秘密情報をレビュー入力へ
含めない／既存の未commit変更を自動で巻き込まない／push・Issue更新は
明示ゲート後のみ／Geminiを全面的に使用しない。

推奨ファイル構成（`.claude/skills/ai-build-council/`配下にSKILL.md・
references・templates・schemas、`.ai-build-council/runs/<run-id>/`配下に
state.json・inputs・design・review・tests・decisions・final）。

models.mdにはモデル名だけでなく役割・禁止事項（読み取り専用フラグ、
編集可否等）をYAML的に定義する。

状態遷移：`INTAKE → DESIGNED → DESIGN_APPROVED → IMPLEMENTING →
TEST_A_PASSED → REVIEWED → FIXING|TEST_B_PENDING → TEST_B_PASSED →
READY_TO_COMMIT → COMMITTED → PUSHED → RECORDED`。失敗テストが残る状態
から`READY_TO_COMMIT`へ進むことは禁止。

Git運用：開始時に`git status`等でbaseline確認、既存変更は勝手に
stash・resetしない、専用branch/worktree推奨、`git add .`禁止、pushは
事前許可時のみ。

Chrome拡張具体例：Manifest V3、`tabs`/`storage`/`action`権限、
`tabs.Tab.audible`での識別、`tabs.update`でのミュート、`storage.sync`
保存。`audible=true/muted=false`「聞こえる」、`audible=true/muted=true`
「再生中だがミュート済み」、`audible=false/muted=true`「ミュート済みだが
無音」の3状態区別が必要。テスト構成はGate A（lint/typecheck/test/build/
e2e）→実装レビュー→修正→Gate B（Gate A再実行＋回帰＋実Chromeスモーク
テスト）。実Chrome検証シナリオを10項目提示（拡張ロード、無音タブ非表示、
音声再生検知、個別ミュート、一括ミュート、サイト常時ミュート、service
worker再起動後の永続性、規則削除後の非自動ミュート等）。

## 不確実な点・前提

GPTとCodex CLIを別議席と数える場合、背後のモデル系列が同じ可能性があり
完全なモデル独立性は保証できない（独立性は別コンテキスト・他回答
非参照・固定入力・編集禁止で担保）。Claude査読サブエージェントの権限
指定はClaude Code版に依存する。Codex CLIのフラグは更新されうるため
preflightでバージョン確認し未知の版では停止する設計が必要。実Chromeの
E2Eはheadless/headfulで挙動差が出うる。「サイト単位」がhostname/
登録可能ドメイン/originのどれかは未確定（5〜7時間規模なら完全一致
hostnameを採用しサブドメイン包括は将来機能とするのが安全）。
`storage.sync`は同期遅延・利用制限があるため受入条件は同一プロファイル
での永続化までに限定するのが妥当。commit・push・Issue更新はリポジトリ
権限とユーザー許可が前提。

### 査読席（Claude）の意見

## 要約

たたき台のワークフローは大枠として妥当（設計→設計レビュー→実装→
テスト→実装レビュー→修正ループ→記録）だが、指摘した5観点すべてに
おいて詰めが甘い。最も重大なのは「議長Fableが実装者兼レビュー結果の
解釈者・裁定者を兼ねる」構造で、"自分が書いたコードは自分でレビュー
しない"という原則を字面上は守っていても、実質的には骨抜きになっている
リスクが高い。また「テスト2回」「バグは通るまで修正」はいずれも上限・
タイミングが未定義で、放置すれば無限ループまたは形骸化した緑化
（テスト削除・弱体化）を招く。結論として、この案は「採用可」ではなく
「構造的な手直しをしてから採用すべき」レベルにある。

## 立場（結論）

現行のたたき台は不採用ではなく修正の上で採用すべき。必須の設計変更：

1. 「レビュー結果の受理／却下」を議長Fableの単独判断に委ねない仕組み
   （バイナリ運用＋人間エスカレーション）を明文化する。
2. 全ループに明示的な回数上限とエスカレーション条件を設ける。
3. Codex CLI等の外部プロセス呼び出しに、タイムアウト・非対話フラグ・
   ハング時の挙動を設計書に明記する。
4. GitHub issue記録はデフォルトOFFの任意機能とし、対象リポジトリ明示＋
   人間の事前承認を必須にする。
5. Chrome拡張機能のような「実ブラウザAPI依存」案件では、テスト
   ハーネス構築を設計フェーズの成果物として明示的に見積もりに含める。

## 根拠

**(1) 自己レビュー回避の原則について**：ai-council_v2では議長Fableは
提案にも査読にも与しない中立的な裁定者だったが、ai-build-councilでは
議長Fableが実装者（著者）であり、かつ実装レビュー結果を「直すか・
却下するか・エスカレーションするか」判断する立場も兼ねる。都合の悪い
指摘を「もう直した」「仕様通り」として握りつぶす余地が構造的に残る。

**(2) テスト2回の運用について**：「実装直後と実装レビュー後の2回」は
固定チェックポイントとしては意味を持つが、"バグは通るまで直す"原則と
矛盾しうる。実装直後のテストが落ちた場合の修正サブループが何回まで
許容されるか記載がない。「2回」ではなく「2つのゲート、各ゲート内部は
グリーンになるまでの上限付きサブループ」と再定義すべき。

**(3) Codex CLIの既知の技術的不具合について**：非対話CLIをサブ
プロセスとして呼び出す設計では、標準入力待ちによるハングが実運用で
よく発生する（非対話/自動承認フラグの指定漏れ、EOFが来ないままの
待機等）。たたき台にはタイムアウト・強制終了・リトライ・
エスカレーションの記載が一切ない。

**(4) 「バグは通るまで修正」の無限ループリスクについて**：上限のない
修正ループは(a)実行時間・コストの青天井化、(b)同一バグへの固執による
停滞、(c)「失敗するテストを緩める／消す」という不正収束、の3リスクを
持つ。「意見の相違」には上限があるが「テストが通らない」という技術的
行き詰まりには同様の上限が明記されていない。

**(5) GitHub issue記録の権限・対象リポジトリについて**：記録先
リポジトリが暗黙のカレントディレクトリか明示パラメータか不明。
GitHub issue作成は「公開コンテンツの投稿」に該当しうる行為であり、
事前の明示同意が必要。ai-council_v2でGrokが任意なのと同様、記録
フェーズもデフォルトOFF・対象リポジトリ明示・実行前確認を必須にすべき。

## 主要な論点

**論点A：自己裁定構造の是正方法**：「実装は議長Fable本体セッションが
直接行い、別プロセスは使わない」制約上、実装と裁定を完全に別
コンテキストに分離することはできない。手続き的分離として、レビュー
指摘は「Fixed / WontFix（要人間承認）/ Disputed（要人間裁定）」の3値
管理とし、議長単独では「WontFix」を確定できないルールにする。
エスカレーション時は議長による要約でなく生コメント・生ログをそのまま
提示する（要約を挟むと同じ利益相反が再発する）。可能であれば「受理／
却下判断」自体を実装の文脈を持たない新規サブエージェントに担わせる。

**論点B：ループ設計の明確化**：設計フェーズにも「設計レビューで重大
指摘→設計やり直し」のループと上限（例：最大2ラウンド）を設けるべき。
実装直後テストの修正サブループ、実装レビュー後の修正サブループ、
それぞれに独立した上限回数（例：各5回）を設定し、超過時は即座に人間
エスカレーションとする。修正ループ中にテストファイル自体が変更された
場合は自動的に警告フラグを立てる。

**論点C：外部CLI呼び出しの堅牢性**：Codex CLI等のサブプロセス呼び出し
には(1)明示的タイムアウト値、(2)非対話・自動承認フラグの固定、
(3)ハング検知時のkill+1回リトライ+失敗時エスカレーション、を設計書
レベルで規定すべき。これは実運用で実際に起きた不具合を踏まえた要件。

**論点D：具体例（Chrome拡張機能）で露呈した見積もり漏れ**：音声タブ
コントローラーのテスト実行を意味あるものにするには、chrome API等を
モックした単体テストに加え、実際の音声再生・ミュート・永続化を検証する
E2Eテスト（Puppeteer等）が必要。このテストハーネス構築自体が実装作業の
一部であり、5〜7時間の見積もりに含まれているかは不明。「テスト実行」
の中身が型チェックやlintのみであれば、実質的には拡張機能が本当に動く
かを何も検証していないことになる。

**論点E：GPTの二重役割**：GPTが「設計提案者」と「実装レビュワー」を
兼ねる構成は、実装レビューが「自分の設計通りに実装されているか」に
偏り、設計自体の欠陥や実現不可能性を率直に指摘しにくくなるリスクが
ある。評価軸を「設計への準拠」ではなく「コードの正しさ・堅牢性・
セキュリティ」に明示的に再定義すべき。

**論点F：Gemini除外の妥当性（軽微）**：制約として受け入れるが、
実装レビューの独立した目がGPT・Claudeの2者のみになる点は、
ai-council_v2の3者構成に比べて多様性が下がる。安全性やセキュリティが
絡む変更では、必要に応じて追加レビュワーをオプトインできる余地を
残しておくとよい。

## 独自の要件定義・設計案

ゲート構造：設計→設計レビュー（上限2ラウンド）→実装→テストゲート1
（内部サブループ上限5回、失敗継続時は実装レビューに進まず即
エスカレーション）→実装レビュー（GPT・Claude独立・ブラインド）→裁定
（実装コンテキストを持たない新規サブエージェントによる3値判定）→
修正ループ（上限5回）→テストゲート2（フルスイート、グリーン必須）→
記録（デフォルトOFF・要人間承認・対象repo明示）。

エスカレーションパッケージの標準化：人間に渡す情報は必ず「diff・全
テスト生ログ（タイムスタンプ付き）・レビュワーの生コメント（要約せず）
・未解決論点の明示リスト」の4点セットとする。

アンチパターンの明文化した禁止事項：修正ループ中のテストファイル変更は
自動フラグ、外部CLI呼び出しは必須タイムアウト＋非対話フラグ＋ハング時
リトライ1回＋エスカレーション、いかなるループも「議長単独の主観的
満足」では終了条件にならない（テスト結果または人間承認のみが終了条件）。

テスト方針の最低ライン：ブラウザAPI等の実環境依存が強い成果物では
「静的解析のみ」を実行結果検証の代替として認めない。単体テスト
（モック）＋最低限のE2E（実ブラウザ／ヘッドレス）の両方を設計フェーズの
成果物として要求し、見積もり時間にハーネス構築コストを別枠計上する。

予算上限：パイプライン全体の総試行回数・想定コスト・想定時間に上限を
設け、超過時は完了未達でも一旦人間に状況報告して継続可否を判断させる。

## 不確実な点・前提

「議長Fable本体セッションが直接実装する」制約の正確な意図が不明で
あり、背景次第では「実装コンテキストを持たない別サブエージェントに
裁定だけ委ねる」提案の実現可能性が変わる。GPT呼び出しがCodex CLI経由で
行われる際の具体的な呼び出し方法によってタイムアウト設定値は変わる。
「実装レビュー後の修正ループ」と「実装直後テスト失敗時の修正」が
たたき台の文言上どこまで同一プロセスとして意図されているか不明。
Chrome拡張具体例の「5〜7時間」見積もりがテストハーネス構築を含むか
不明。GitHub issue記録の権限まわりのリスクは一般的な注意喚起にとどめた。

## Stage 2: 相互レビュー

### 提案席（GPT）のレビュー

## 賛成する点

自己裁定構造の問題、ループ上限、Codex CLIハングへの対処、GitHub issue
記録、Chrome拡張のテスト見積もり漏れ、GPTの二重役割——査読席の6指摘
すべてに賛成。

指摘の状態は`Fixed`（修正済み、再テスト・再レビューで確認）／
`WontFix`（人間の明示承認が必要）／`Disputed`（人間が採否を裁定）の
3値とし、Fable単独で確定できるのは`Fixed`のみとする。

Test Gate A/Bはそれぞれ最大5回とし、同一原因3回連続／環境障害2回連続／
ゲート試行5回到達／テスト削除・緩和なしには通せない／予算超過、の
いずれかで早期停止・エスカレーション。

Codex CLIは非対話モード・stdinクローズ・プロセス単位タイムアウトを
設定。一定時間出力・CPU・対象ファイルの変化がなければハング候補とし、
プロセスツリーを終了して1回だけ再実行、再発時はエスカレーション。

GitHub issue記録はデフォルトOFF、対象リポジトリ・公開範囲・投稿内容を
示し実行前に人間の明示承認を必須とする。commit/pushも同様。

Chrome拡張のテスト見積もりについて、ハーネス未整備なら5〜7時間の
見積もりに当然含める必要がある。ハーネス構築・CI統合・ブラウザ差異
調査は本体実装と分けて見積もるべき。

GPTの二重役割について、実装レビューの評価軸は(1)機能的正しさと要求
充足 (2)安全性・セキュリティ・データ損失リスク (3)エラー処理・競合・
境界条件 (4)テストの妥当性と不足 (5)保守性・既存コードとの整合 (6)
凍結済み設計との差異、の順とする。

## 反対する点

「diffとレビューコメントのみ」を渡した裁定者に受理・却下判断を委ねる
案には完全には賛成しない。要求仕様・テスト結果・変更対象の制約を
渡さないと、正しい修正を誤って不要と判断する可能性がある。裁定者には
著者の思考過程や会話履歴は渡さず、固定diff・レビュー指摘・凍結済み
要件・関連テスト結果・必要最小限のリポジトリ文脈を渡すべき。

各テストゲート一律5回という固定値にも反対。デフォルト5回としつつ、
開始前に人間が変更できる設定値にする（実行中にエージェント自身が
上限を引き上げることは禁止）。

## 追加提案

8ステージへの改訂：0.Intake・隔離・予算設定（対象・禁止操作・成果物・
テスト範囲・試行上限・時間コスト上限・外部公開操作の可否を確定）→
1.独立設計（要件・受入条件・テスト戦略・E2Eハーネスの要否）→2.設計
査読・凍結（変更には記録と承認）→3.Fable本体実装（設計上の問題発見時は
再承認へ戻る）→4.Test Gate A（テスト緩和は設計変更として扱う）→
5.固定diffの独立コードレビュー（正しさ中心、実装者の説明は先に見せない）
→6.指摘処理・Test Gate B（Fixed/WontFix/Disputed追跡、Fableは
WontFix単独確定不可）→7.成果確定・commit/push・記録。

横断的な不変条件：実装者はレビュー指摘を消去・非表示にできない、
テストコードの変更は本体コードの変更と分離してレビュー、失敗テストを
skip/削除/期待値緩和で通す場合は人間承認が必要、レビュー対象固定後に
diffが変わった場合はレビュー結果を流用しない、CLI実行ごとに終了コード・
経過時間・タイムアウト・再試行理由を記録、機密情報をログ・issue・
レビュー入力へ含めない。

## 未解決の論点

WontFix/Disputedの人間裁定を誰がどの期限で行うか。人間が応答しない
場合の安全な終了・保存方法。Test Gate A/Bの試行上限・時間上限・コスト
上限の標準値。独立裁定エージェントへ渡す「必要最小限の文脈」の具体的
境界。Chrome拡張E2Eで保証するブラウザ・OS・Manifestバージョン・CI環境
の範囲。commitまでを内部操作として包括承認できるか。凍結後に要件の
欠陥が判明した場合の再設計フローと既存レビュー結果の失効範囲。

### 査読席（Claude）のレビュー

## 賛成する点

Stage0の3分類とaccepted/modified/rejected/deferred＋理由の必須化は、
私の前回案にはこの粒度の受け入れ判定フレームがなく、提案席の方が優れて
いる。`--sandbox read-only`（設計・査読席）と`workspace-write`をFable
本体のみに限定する技術的強制は、私が「手続き的な自己裁定回避」しか
提案できなかった部分を、OS/プロセスレベルのサンドボックス制約という
技術的強制に落とし込んでいる。固定diffレビュー（ハッシュ固定、変更で
失効）は私が指摘していなかったレースコンディションを潰している。
停止ロジック（原因の性質に応じた止め方）は私の「一律上限」案より実務的。
`git add .`禁止、push・Issue記録の事前許可ゲートの方向性、Chrome拡張の
audible/muted 4状態区別と実Chrome検証シナリオ10項目にも賛成。

## 反対する点

minor項目の「理由付き却下」判断者が依然としてFable本体である点。
blocker/majorは客観的再テストにより自己申告リスクがほぼ消えているが、
minor項目は却下判断が誰にどう可視化されるか不明で、規模を縮小しただけで
自己裁定の芽が残っている。

Codex CLIのハング対策が依然として明示されていない点。「環境障害2回
連続」は反応的検知だが、ハングは多くの場合「失敗」ではなく「応答なしで
停止」であり、タイムアウト設定がなければ2回のカウントにすら到達しない。

「同一原因」の判定基準が未定義。エラーメッセージの完全一致か、
スタックトレースのハッシュか、レビュワーの主観判断か不明。

GPT（Codex）の設計提案者と実装レビュワーの二重役割が未解消。Stage1で
設計したCodexが実装レビューも担当する構成は変わっていない。

テストハーネス構築コストが5〜7時間の見積もりに反映されているか不明。

## あなたの指摘への対応状況

1. 自己裁定構造の問題：大部分解消、一部残存（minor項目の却下判断は
   Fable自身のまま）
2. ループ上限の未定義：解消（「同一原因」判定基準自体は未定義）
3. Codex CLIハング対策の欠如：未解消（部分的にのみ緩和）
4. 「バグは通るまで修正」の無限ループリスク：解消
5. GitHub issue記録の権限・対象リポジトリ：部分的に解消（push同等の
   ゲートがIssueに明示されているか確認できず）
6. テストハーネス構築の見積もり漏れ：部分的に解消
7. GPTの二重役割：未解消

## 追加提案

Issue/PR作成にもpushと同じ事前許可ゲートを適用し対象リポジトリを明示
パラメータにする。「同一原因」の操作的定義（失敗テスト名＋トップ
スタックフレームの一致、またはエラー型＋アサーション内容の一致）を
明文化する。Codex CLI呼び出し全般に明示的なプロセスタイムアウトと
kill＋1回リトライを追加する。minor項目の却下理由をStage7の記録時に
一覧としてログに残す。Chrome拡張のような案件では見積もりを「コア実装」
と「テストハーネス構築」に分けて再提示する。Stage5でCodexが実装
レビューを行う際の評価基準を「正しさ・堅牢性・セキュリティ」に限定する
よう明示する。

## 未解決の論点

minor項目の却下判断における残存する自己裁定リスク。Codex CLIのハング
防止の具体的なタイムアウト値・リトライ回数。「同一原因」判定の運用
定義。Issue/PR記録における許可ゲートの明文化とリポジトリ明示化。
Chrome拡張例におけるテストハーネス構築時間の見積もり反映。GPTの
設計提案者・実装レビュワー二重役割の解消方法。

## Stage 3: 統合・裁定（議長）

両席の意見はかなり収束した。GPTがほぼ全面的に指摘を受け入れて8ステージ
案に改訂した一方、査読席は最終レビューで7論点のうち5つは解消、2つ
（GPTの二重役割、Codex CLIハングの根本対策）が未解消と判定した。

**裁定：条件付き承認**

議長が追加で裁定した条件：

1. GPTの二重役割：設計（Stage1）と実装レビュー（Stage5）のCodex CLI
   呼び出しは必ず別の新規セッションとする（対話継続・要約引き継ぎ
   禁止）。同一プロバイダである以上完全な独立性は保証できないが、
   セッション分離によりアンカリング効果を構造的に低減する。第3ベンダー
   による完全独立は、Gemini除外・Grok任意という既存方針とのバランスで
   見送る。
2. Codex CLIハング対策：全呼び出しに非対話モード・stdin `/dev/null`
   クローズ・タイムアウト（デフォルト10分）・無応答時kill+1回リトライ+
   エスカレーションを標準仕様として明記する（今回の運用で実際に発生
   した48分ハングを踏まえる）。
3. 「同一原因」の判定基準：失敗テスト名＋トップスタックフレーム一致、
   またはエラー型＋アサーション内容一致で運用定義し、判定根拠をログに
   残す。
4. push・Issue/PR作成は同等の事前承認ゲートとし、対象リポジトリを
   明示パラメータにする。
5. minor指摘の却下はFable単独で可とするが、理由を全件ログに残し記録
   フェーズで人間が事後確認できるようにする。
6. Chrome拡張等の実ブラウザAPI依存案件は、コア実装とテストハーネス
   構築の見積もりを分離して提示する。
