## 要約

課題文の依頼1（新規15案）と依頼2（ロードマップ）に、査読席としての成果物を提示する。あわせて、課題文および既存2回分の稟議書に含まれる**事実誤認3件・数値誤り1件・未指摘の重大リスク3件**を指摘する。

結論を先に言えば、**今回の会合で最も価値のある成果物は「新規15案」ではなく「44案のうち何を捨てるか」の決定**である。現状は在庫（実装済み・未公開）15本に対し公開4本、未着手21本という状態であり、ここに15案を足す行為は、第2回裁定の条件1「実装キューへそのまま積み増さない」に実質的に反する。したがって私は15案を提示するが、**バックログへの純増としてではなく、既存案の置換・統合の受け皿として**位置づけ、追加と同数以上の打ち切りを条件とする。

特に重大な指摘は3点である。

1. **E-18の設計変更は不要だった可能性が高い。** 第2回で「`chrome.downloads`に事後改名手段が存在しない」ことから「クリップボードにコピーして保存ダイアログで貼り付ける」設計へ転換したが、`chrome.downloads.onDeterminingFilename`（`suggest()`コールバック）でダウンロード前にファイル名を決定できる。事後改名が不可という命題は正しいが、そこから導いた設計転換は誤りで、既定オフのChrome設定に依存する使い物にならない仕様が確定してしまっている。
2. **同一デベロッパーアカウントから類似UXの小型拡張を短期に大量公開することは、Chrome Web Storeのスパム／重複コンテンツ方針と最小機能性方針に抵触しうる。** この論点は既存2回の稟議書に一度も登場しない。44案の設計思想（1機能=1拡張）と真正面から衝突する構造的リスクであり、しかも制裁はアカウント単位で全拡張に及ぶ。
3. **F-21（電車遅延）は「トークン待ち」ではなく「アーキテクチャ上不成立」の疑いが強い。** APIトークンを配布物に同梱すれば全ユーザーに秘密鍵を配ることになり、規約・セキュリティの両面で成立しない。プロキシサーバーは1日MVPの範囲外。トークンが届いても再開すべきでない。

数値誤り：**課題文が4箇所で言う「未提出16案」は15案が正しい**（A〜C:10本＋D〜H:5本）。

**新16. インストール済み拡張機能の権限棚卸しレポート**
- 概要：インストール済みの全拡張機能を、要求している権限の危険度（全サイトのデータ読み取り／閲覧履歴／ダウンロード／クリップボード等）で分類し、「このサイトのデータをすべて読み取れる拡張は5本あります」という形で人間可読なレポートにする。有効／無効の切替と、無効化の記録もその場で行える。
- 誰の困り事を解決するか：拡張を10本以上入れているが、どれが何を見られるのか把握していない人。社内PCの棚卸しを求められた情シス担当。家族のPCを見てあげる人。
- なぜ需要があると思うのか：`chrome://extensions`は1本ずつカードを開かないと権限が見えず、横断比較ができない。拡張経由の情報流出は定期的にニュースになり、棚卸しの動機は反復的に発生する。個人開発者本人にとっても、シリーズで自作拡張を増やすほど自分で必要になる。
- Chrome API：`management`・`storage.local`。**教訓1の分類：(c) ページ非接触**（content scriptを一切注入せず、Webページの内容に触れない）
- 実装難易度：低／販売難易度：中（「セキュリティ製品」と誤認されないよう、危険度は「権限の広さ」であって「悪意の有無ではない」と明記が要る）
- 収益化方法：無料。単独では課金しない（後述の理由により、当面シリーズ全体で課金しない方針を推奨）
- 将来の拡張案：サイトごとの通知・位置情報・カメラ許可の棚卸し（`contentSettings`）へ横展開。ただし別拡張にはせず本体に統合する
- 実装時間の目安：4〜6時間（うち権限の危険度分類テーブルの整備に半分）
- 既存44案と重複しない理由：44案に`management` APIを使う案は1件もなく、「拡張機能自体を対象にする」案も存在しない
- 提出負担：**最小級**。ページ内容を一切扱わないためプライバシー開示が1行で済む。ただし`management`は審査で使用理由の説明が要る（後述リスク）

### 依頼2：実装ロードマップ

#### 論点1：提出と新規実装のどちらを優先するか

**提出を優先する。** Phase 1では時間配分を**提出9：新規実装1**とし、未提出在庫が5本以下になるまでこの比率を維持する。根拠は4つ。

1. **在庫は劣化する。** 実装済み・未公開の資産は時間とともに価値が下がる。Chromeのバージョン更新、MV3の仕様変更、対象サイトのDOM変化により、公開時には再検証と修正が必要になる。特にC-14（MutationObserver）、D-16（フォーム構造依存）、G-24（議事録アプリ依存）は劣化が速い。今日出せば0.5〜2時間で済むものが、3か月後には5時間かかる。
2. **公開しない実装はシリーズの目的を1つも達成していない。** 目的は「公開しながら経験を積む」であり、審査対応・ストア運用・レビュー対応・ユーザー問い合わせという、実装では絶対に得られない経験がすべて公開の向こう側にある。実装だけを反復しても、同じ経験を繰り返しているにすぎない。
3. **需要根拠が全案「推論」である以上、検証手段は公開しかない。** 第2回裁定の条件5（競合調査）は未消化のままだが、そもそも競合調査より実際の公開の方が強い証拠を返す。実装を増やしても仮説は1つも検証されない。
4. **単位時間あたりの産出が5倍違う。** 実装済み1本の提出は、型ができていれば0.5〜1.5時間。新規実装は4〜9時間＋提出作業。「公開本数」を産出物とみなすと、提出作業の生産性は新規実装の5倍前後である。

ただし**提出ペースには上限を設ける**。後述するスパム／重複コンテンツ方針のリスクと、審査キューの詰まりを避けるため、**週2本まで、同時に審査中の拡張は3本まで**とする。したがって「提出優先」は「全部一気に出す」を意味しない。

#### 論点2：未提出15案を全て提出すべきか（打ち切り基準）

**全ては出さない。** 以下の6基準を設け、**2つ以上該当したら打ち切り、1つ該当なら統合を検討**する。

- **基準A（重複）**：既に公開済み、または他の未提出案と、機能・コンテンツ・UXが「高度に類似」している
- **基準B（最小機能性）**：ストア説明文で「なぜブックマークレットやブラウザ標準機能ではなくこれが必要か」を1文で書けない
- **基準C（外部依存が塞がっている）**：外部API・外部設定・対象サイトの許諾に依存し、その依存が現時点で解消されていない
- **基準D（保守負債が価値を上回る）**：対象サイトのDOMや外部仕様の変化に、月1回以上の追従が要る見込み
- **基準E（ドッグフーディング）**：作者本人が直近1か月で一度も使っていない
- **基準F（開示過重）**：プライバシー開示が重い（履歴・全サイト・入力内容の保存など）のに、需要根拠が推論のみ

基準Eを入れる理由は、これが唯一、机上ではなく事実に基づく基準だからである。他5基準は判断が割れうるが、Eは記録を見れば決まる。**在庫15本に対してまずEを適用し、使っていないものを候補として炙り出すことを推奨する**（判定は作者本人にしかできないため、ここでは名指ししない）。

#### 論点3：Store提出のハードルを下げる仕組み

**まず順序を正す。自動化に投資する前に実測せよ。** 課題文は「4案を公開した実績があるため再利用可能な型があるはずである」と述べるが、これは仮説であって観測ではない。滞留の原因が「準備作業が重い」なのか、それとも別（優先順位付けがされていない／公開して評価されることへの心理的抵抗／単に次の実装の方が楽しい）なのかが特定されていない。前者でなければ自動化投資は空振りする。

**Phase 0の最初の作業は、既に公開した4案について「提出の各工程に実際に何分かかったか」を思い出せる範囲で書き出すこと**とする。所要30分。ここで「1本あたり3時間かかった」なら自動化が効き、「1本あたり40分だった」なら原因は別にある。

そのうえで、型化の具体案を示す。

**(1) 提出キット・リポジトリを1つ作る（投資6〜10時間、以後全案で再利用）**

- **権限説明の定型文ライブラリ**：`activeTab` / `storage` / `contextMenus` / `alarms` / `notifications` / `scripting` / `downloads` / `tabs` / `bookmarks` / `sidePanel` / `commands` / `management` / `history` / `omnibox` の各権限について、「いつ使うか／何のために使うか／それ以外に使わないこと」の3文を穴埋め形式で用意する。既に4案分で実際に書いた文章があるはずで、それを転記するだけで7〜8権限は埋まる。以後、新規拡張の権限説明は「該当行をコピーして固有名詞だけ差し替える」作業になる
- **単一用途説明の型**：「この拡張機能は、〈対象〉に対して〈単一の動作〉を行うためだけのものです。〈やらないこと〉は行いません。」の1文テンプレート
- **プライバシーポリシーのテンプレート**：GitHub Pagesで`https://<user>.github.io/privacy/<ext-name>`の形で1リポジトリ内に全拡張分を置く。本文の差分は「収集するデータ」の表だけになるよう設計する。多くの案は「一切収集しない」の1行で済む
- **ストア説明文の型**：①1行要約 ②困り事 ③使い方3ステップ ④権限の説明 ⑤「データを外部に送信しません」宣言 ⑥制限事項（対応しないページ・既知の非対応）。⑥を型に入れておくことが重要で、後からの低評価レビューの多くは「できると思ったのにできなかった」に由来する

**(2) スクリーンショットの半自動生成（投資2〜4時間）**

Puppeteer / Playwrightで、`--load-extension`により拡張を読み込んだChromeを起動し、ポップアップ／オプション／サイドパネルのURL（`chrome-extension://<id>/popup.html`）を1280×800の固定ビューポートで開いてキャプチャする。上に日本語のキャプション帯を合成する。1本あたりのスクショ作成が30〜60分から5〜10分になる。**ただしこれはUIのスクショにしか効かず、「実際のWebページ上で動いている様子」のスクショは手動が残る**。効果は案の性質による（新16・新20・新24・新29のようなページ非接触の案では効果が大きく、新18・新22のようなページ上で動く案では小さい）。

**(3) 提出前lintスクリプト（投資2〜3時間）**

manifest.jsonに対して、name ≤ 45文字、description ≤ 132文字、icons 16/48/128の存在、version形式、`permissions`の各項目に対応する説明文がキットに存在すること、`host_permissions`が空であること（原則）、を機械的にチェックする。各リポジトリのCIに置く。**「提出直前に気づいて手が止まる」を潰すことが目的**であり、時間短縮より心理的な障壁の除去に効く。

**(4) 手動テスト票のテンプレート**

第2回で決めた9項目の仕様テンプレートと1対1対応する受入確認票を作り、チェックを入れるだけにする。SW再起動後の復元、権限取消時の挙動、`chrome://`ページでの失敗表示、シークレットモードは全案共通の確認項目になる。

**(5) 自動化できないものを明示しておく**

審査待ち時間（数日〜2週間、権限が多いほど長い）、ポリシー適合の判断、レビューへの返信、Chromeの破壊的変更への追従。これらは本数に比例して増える一方であり、**公開本数を増やすことは保守負債を増やすことでもある**。この論点は既存2回の稟議書に一度も現れていないが、20本を公開すれば毎月の保守だけで相当の時間を消費する。**本数を目標にする前に、保守を打ち切る条件（何をもって「この拡張は更新しない」と宣言するか）を先に決めるべきである。**

#### 論点4：保留中3案の処理

**F-21（電車遅延・ODPTトークン待ち）→ 打ち切り。**

トークンが届いても再開すべきでない。理由は、拡張機能というクライアント配布物にAPIトークンを同梱する行為が、(a) 全ユーザーに開発者の認証情報を配布することと等価であり、(b) 拡張のパッケージは誰でも展開して中身を読めるため秘匿できず、(c) 多くのオープンデータAPIの利用規約は認証情報の第三者提供・再配布を禁じている、という三重の問題を抱えるためである。回避策は2つしかない。

- 開発者が中継サーバーを運用し、トークンをサーバー側に置く → 1日MVPの範囲を大きく超え、恒久的な運用コスト（可用性・費用・障害対応）が発生する。シリーズの前提と両立しない
- 各ユーザーに自分でトークンを取得させ、拡張の設定画面に入力させる → 技術的には成立するが、開発者登録を経ないと使えないため、対象ユーザーが「開発者登録を厭わない人」に限定される。「電車の遅延をバッジで見たい一般利用者」という需要層は消滅する

したがって本案は「トークン取得待ち」という保留状態にあるのではなく、**設計上成立していない**。保留のまま置くと、いつまでもバックログを占有して判断コストを払い続けることになる。打ち切りを推奨する。

**G-23（行政ルビ表示・設計査読指摘対応待ち）→ 今期は着手しないと明示的に決定し、バックログ最下段へ。**

打ち切りではないが、「対応待ち」という宙吊り状態を解消する。理由は3点。(a) 辞書同梱により拡張サイズと初回ロードが重くなり、他の案（4〜7時間）と比べて明らかに割高、(b) 行政手続きという文脈で読みが誤ると、単なる不便ではなく実害につながりうる品質要求の高さ、(c) 在庫12本の出荷が最優先である時期に、最も重い案に着手する理由がない。**「保留」は判断ではなく判断の先送りであり、在庫を生む元凶である。「今期やらない」と決めることが判断である。**

**G-25（透かし追加・見積り30〜44h）→ MVPを再定義し、G-26および新21と統合して1本にする。**

まず、**30〜44時間という見積りは、そもそもシリーズの前提「1日程度で完成」と矛盾しており、第1回から検出されるべきだった。**見積りが正しいならこの案は最初から条件違反であり、見積りが過大ならその根拠が問われる。私は後者だと考える。実績を見れば、約12日間で19本の実装が完了しており、これは「1本あたり4〜9時間」という見積りと整合しない（19本×4時間でも76時間、12日で消化するには1日6時間以上を毎日実装だけに費やす計算になる）。**見積り体系が実績に対して未校正である。**

再定義案：入力はPNG/JPEGのみ、テキスト透かしのみ（画像透かしは対象外）、位置は9分割グリッドから選ぶだけ（自由配置なし）、EXIF Orientationは対応せず「回転が正しく反映されない場合があります」と明記。これで8〜12時間に収まる。

そのうえで**G-25（透かし）・G-26（ぼかし）・新21（証跡キャプチャ）を「アップロード前・保存前のローカル画像加工ツール」1本に統合する**。3本を別々に公開すると、いずれも「Canvasでローカル画像を加工してダウンロードする」拡張であり、基準A（重複コンテンツ）に真正面から抵触する。統合すれば単一用途の説明も成立する（「ユーザーが選んだ画像をローカルで加工し、保存する」）。統合版の実装見積りは12〜16時間。

#### 論点6：成功指標

**現状の指標設定には問題がある。指標が明示されていないため、事実上「実装本数」が指標として機能してしまっている。**これは最悪の指標である。実装本数は在庫を増やすだけで、それ自体は何の価値も生まず、時間とともに劣化し、保守負債を先送りするからである。「12日で19本実装」という実績は、この指標に沿った最適化が実際に起きていることを示している。

指標を以下に組み替える。

**(1) 完了の定義を変える（最重要）**

`完了 = Chrome Web Storeで公開済み`。実装完了は0点とする。第2回の条件2は「Store提出準備完了ゲートを通過するまで完了扱いにしない」だったが、これでも足りない。**「提出準備完了」という中間状態を作ると、そこに新しい在庫が溜まるだけである。**中間状態を廃し、公開のみを完了とする。

**(2) 主指標：公開本数（ガードレール付き）**

- 目標：6か月後に累計公開16本以上（現在4本）
- ガードレール：**審査却下ゼロ／ポリシー警告ゼロ／同時審査中3本以下**。ガードレールを外して本数だけ追うと、スパム・最小機能性の方針に抵触してアカウント全体が危険にさらされる。本数目標にはこの制約が不可欠

**(3) 補助指標：フロー効率**

- **リードタイム中央値**：実装完了から公開までの日数。目標7日以内
- **WIP（未提出在庫）**：上限5本。**これは目標ではなく制約**であり、上限を超えたら新規実装を停止する

**(4) 学習指標：シリーズの目的に対する直接指標**

シリーズの目的が「経験を積む」である以上、これを測る指標が必要である。**「新規に習熟したChrome API／機能領域の数」**を四半期ごとに数える。現状、44案は`contextMenus`＋`storage.local`＋`alarms`＋`activeTab`の組み合わせに大きく偏っており、11本目の`contextMenus`拡張から得られる学習は1本目の1割にも満たない。今回の新規15案で`management`・`omnibox`・`chrome_url_overrides`・`history`・`captureVisibleTab`・`downloads.search`を含めたのは、この観点に基づく。

**(5) 需要指標：目標ではなく観測として置く**

公開30日時点のインストール数と評価を記録する。**ただしこれを「目標」にしてはならない。**個人開発の小型拡張のインストール数は、宣伝・タイミング・ストア内検索といった制御不能な要因に強く左右されるため、目標にすると制御できないものに責任を負うことになる。あくまで「需要仮説が当たったか外れたか」の学習記録として使う。目安として「30日でインストール10件未満なら仮説は外れ」と事前に定義し、外れた案は宣伝で挽回しようとせず、そのまま記録して次に進む。

**(6) 収益は当面、指標から外す**

理由は3つ。(a) Chrome Web Storeの組み込み決済は第1回で確認済みのとおり廃止されており、課金には外部決済とライセンス検証の基盤が別途必要になる。(b) それは「1日MVP」の範囲外であり、44案の「収益化方法：Pro版で…」という記述は現時点ですべて実現手段を欠いている。(c) さらに、有料販売を行うと日本では特定商取引法に基づく表記（氏名・住所・電話番号）が必要になり、Chrome Web Store側でもEU向けにtrader（事業者）ステータスの申告が求められ、事業者情報が公開される。**個人開発者にとって実名・住所の公開は無視できないコストであり、これを「Pro版で収益化」の一言で済ませている44案の記述はすべて不正確である。**収益化は、公開本数が二桁に達し、インストール数で上位の案が特定できてから、単一の案に対して検討すべきである。

## 根拠

**提出優先の根拠**は前掲のとおり在庫の劣化・目的適合性・仮説検証手段・単位時間産出の4点である。このうち最も強いのは第2点で、シリーズの目的が「Chrome Web Storeへ公開しながら経験を積む」と明記されている以上、公開しない実装は定義上、目的を達成していない。

**打ち切りを重視する根拠**は、第2回裁定の条件1（積み増さない）が既に一度出されているにもかかわらず、その後に実装が5本進み在庫がさらに増えたという事実である。条件を課しても在庫が増えたということは、**条件の形式（「積み増さない」）が弱すぎた**ことを意味する。「積まない」は行動を制限するだけで既存の在庫を減らさない。減らすには「捨てる」という積極的な行為が要る。今回の会合で15案を追加するなら、同時に捨てる決定を伴わない限り、第2回と同じ結末になる。

**指標の組み替えの根拠**は、現状で実装が19本進み公開が4本という配分そのものである。人は測られるものを最適化する。実装本数だけが可視化されていれば実装が進む。公開本数を主指標に据え、未提出在庫を上限付きの制約として明示することで、初めて行動が変わる。

**新規15案の設計方針の根拠**は教訓11である。教訓11は「提出のハードルもスコープ検討に織り込め」と述べるが、実際に効くのは**ページ内容に触れない案を選ぶこと**である。ページ内容に触れなければ、プライバシー開示は「収集しない」の1行、権限説明は2〜3項目、単一用途説明は1文で済む。今回15案のうち5案（新16・新17・新20・新24・新29）をこの類型に置いたのは、出荷スプリント期でも工程を乱さずに実装できる案を確保するためである。

## 主要な論点

査読席として、課題文および既存2回の稟議書に含まれる誤り・リスク・矛盾・欠落を指摘する。

### 論点A：事実誤認 — E-18の設計転換は不要だった（重大）

第2回で「`chrome.downloads`に任意のローカルファイル名への事後変更手段（rename等）は存在しない」と確定し、これを根拠に「ダウンロード前に候補名を生成しクリップボードへコピー、ユーザーが保存ダイアログで貼り付ける」設計へ転換した。この転換には2つの問題がある。

1. **`chrome.downloads.onDeterminingFilename`が考慮されていない。**このイベントは、ダウンロードのファイル名が決定される前に発火し、リスナー内で`suggest({filename, conflictAction})`を呼ぶことで、拡張がファイル名を決定できる。事後の改名ができないという命題は正しいが、**製品目的（ダウンロードするファイルに自動で意味のある名前を付ける）は事前決定で完全に達成できる。**クリップボード＋手動貼り付けという迂回は不要である。
2. **転換後の設計が、既定でオフのChrome設定（「ダウンロード前に各ファイルの保存場所を確認する」）に依存している。**これは第2回自身が認識し「説明文と初回セットアップ画面に明記する」で処理したが、**設定変更を前提とするツールは、インストール直後に動かないという体験を全ユーザーに与える。**低評価レビューを招く典型的な構造であり、「明記すれば良い」で済む問題ではない。

したがって**E-18は現状のまま提出すべきでなく、`onDeterminingFilename`ベースで再設計すべきである**（Phase 2に配置した）。なお、`onDeterminingFilename`はデフォルトのダウンロードフォルダ配下（サブディレクトリ含む）にしか置けず、複数拡張が同時にリスナーを持つと競合しうる、という制約は別途要件に含める必要がある。この指摘は私の知識に基づくもので、**実装着手前に現行の公式ドキュメントで裏を取ること**を条件とする。

### 論点B：未指摘の重大リスク — 大量公開そのものがポリシーリスクである（重大）

既存2回の稟議書、および今回の課題文には、**「同一デベロッパーアカウントから類似した小型拡張を多数公開すること」自体のリスク**が一度も現れない。しかしChrome Web Storeのデベロッパープログラムポリシーには、少なくとも以下の2つの関連条項がある。

- **スパム／重複コンテンツ**：機能・コンテンツ・ユーザー体験が高度に類似した複数の拡張を公開すること
- **最小限の機能性**：単一の些細な機能しか持たず、ブックマークレットやWebページで代替できる拡張

44案の設計思想は「単一用途・1機能=1拡張」であり、これは審査の単一用途要件には適合するが、**同時に上記2条項への距離を最小化する方向にも働く。**特に危険な近接群を名指しすると、

- **選択テキスト整形群**：A-4（Markdown引用）／A-5（整形コピー）／新1（クリップスタック）／新13（日付フォーマット）／新14（表Markdown変換）── 5本
- **読みやすさ群**：C-12（ズーム記憶）／C-13（拡大リーダー）── 2本、#23（ルビ）を加えると3本
- **ローカル画像加工群**：G-25（透かし）／G-26（ぼかし）── 2本、私の新21を加えると3本
- **alarms＋バッジ通知群**：A-2（リンク期限）／新4（更新期限）／F-21（遅延）── 3本（第2回は「パターンの反復」として多様性の観点から除外を判断したが、これは審美の問題ではなくポリシーの問題でもある）
- **ブックマーク群**：A-3（受信箱）／新6（読了管理）── 2本

かつ、**制裁はアカウント単位で及びうる。**1本の違反判定が、公開済みの他の拡張すべてに波及する構造になっている。19本すべてを1アカウントにぶら下げることは、集中リスクでもある。

これがロードマップで統合を繰り返し推奨し、提出ペースに上限（週2本・同時審査3本）を設けた理由である。**「本数を増やす」という戦略は、ある本数を超えると逆向きのリスクに転じる。**その閾値がどこかは公開情報から確定できないが、閾値の存在を前提に設計すべきである。

### 論点C：数値誤り — 未提出は16案ではなく15案

課題文は4箇所（本文75行、214行、220行、222行）で「実装済み・Store未提出が16案」とする。しかし課題文自身の2つの表を数えると、A〜Cで10本（A-4、A-5、A-6、B-8、B-9、B-10、C-11、C-12、C-13、C-14）、D〜Hで5本（D-15、D-16、E-18、G-22、G-24）、合計15本である。総数の検算も合う（公開4＋未提出15＋保留3＋未着手21＋不採用1＝44）。

1本の差は結論を変えないが、**ロードマップの計画数値の基礎が検算されずに4回繰り返されている**という事実は、他の数値（G-25の30〜44時間、各案の実装時間目安）についても同種の未検算がありうることを示唆する。実際、次の論点Dがそれである。

### 論点D：矛盾 — 見積り体系が実績と整合していない

第1回の会合日が2026-07-20、第2回が2026-07-21、今回が2026-08-02である。この間に19本（A〜C 14本＋D〜H 5本）の実装が完了している。約12日で19本、すなわち1日1.5本を超えるペースである。一方、44案の実装時間目安は1本あたり3〜9時間、合計すれば100時間を優に超える。**両者は整合しない。**考えられる説明は3つで、いずれも意思決定に影響する。

1. 見積りが実態に対して数倍過大である（AI支援を前提とした実際の生産性が織り込まれていない）
2. 「実装済み」の水準が、見積りが想定する完成度に達していない（テスト・エッジケース処理・提出可能な品質に至っていない）

### 論点E：矛盾 — 「1日で完成」という前提と、実際の運用が乖離している

### 論点F：欠落 — 判定基準に「提出容易性」と「保守負債」がない
