# 検討テーマ

Chrome拡張機能の開発シリーズについて、以下2点を検討せよ。

1. **既存44案（後述）と重複しない新規アイデアを15案提案せよ。**
2. **既存44案＋今回の新規案の全体から、次に着手すべき案を選定し、実装ロードマップを策定せよ。**

## 背景：これは何の一部か

個人開発者が「1日程度で完成できる小さなChrome拡張機能」を継続的に作り、
Chrome Web Storeへ公開しながら経験を積むシリーズの3回目の検討である。

- 第1回：29案のアイデアリストを策定（項目1〜29、A〜Hカテゴリ）
- 第2回：D〜H（項目15〜29）の要件を実装経験からの教訓で再定義し、新規15案（新1〜新15）を追加
- 第3回（今回）：さらなる新規案の追加と、全体の実装ロードマップ策定

実装体制は Claude Code + Codex CLI による並列独立レビュー、
`ai-build-council` というゲート付き実装ワークフロー
（独立設計→設計査読→実装→テスト→固定diffの独立実装レビュー→修正→記録）。

## 判定基準（統合・裁定で重視する観点）

- 目的適合性：個人開発者が実装可能な規模か／シリーズの目的（公開実績を積む）に資するか
- 制約充足：Manifest V3、Chrome Web Store審査を通せるか（最小権限・単一用途・リモートコード不使用）
- 根拠の強さ：需要・差別化の裏付け
- リスク：技術リスク・審査リスク・法務リスクが具体的に評価されているか

# A〜C実装で得られた教訓（11項目）

## 権限設計・審査運用

1. **オリジン単位オプトインアーキテクチャ**：常駐content_script・広範なhost_permissionsを使わず、ユーザーが明示的に有効化したサイトにのみ`optional_host_permissions`で動的にcontent scriptを登録する設計が確立した。ただし第2回会合で、これは2パターンに分けるべきと確定した：
   - 少数の**既知ドメインに常時作用**させたい場合 → `optional_host_permissions`によるサイト単位オプトイン
   - **不特定多数のドメインで単発実行**したい場合 → `activeTab`によるオンデマンド実行
2. **Chrome Web Store審査では、manifestの`permissions`ひとつひとつに「使用理由」の記入が求められる**（1権限あたり、いつ使うか／何のために使うか／それ以外に使わないこと）。権限が広い・多いほど審査が長引く。
3. **「単一用途（Single Purpose）」の説明を審査で必須提出する。** 1拡張機能=1目的で設計しないと自己矛盾が生じる。

## 非同期・状態管理（繰り返し発生した問題パターン）

4. **TOCTOU競合が複数の案で独立に発見された。** 保存判定後・書き込み前にオリジンが無効化される（C-11）、タブが検証後に別URLへ遷移する（B-8）、権限ダイアログ操作中にタブが別オリジンへ遷移する（C-14）。**非同期処理をまたいで前提条件を再確認する設計**を最初から要件に含めること。
5. **`chrome.alarms`の一回限りalarmは発火後にChrome側で自動削除される。** これを「異常」と誤認識して再作成すると、過去時刻でのalarm再作成→即再発火→二重通知になる（B-9）。alarm消失は正常系。
6. **Service Worker再起動を前提にした設計が必須。** インメモリの追跡状態だけに依存すると再起動で機能停止する（B-7）。`storage.session`（プロセス生存中のみ）と`storage.local`/`sync`（永続）の使い分けを要件段階で明示すること。「`storage.session`をブラウザ起動時にTTL掃除する」設計は自己矛盾（C-13）。
7. **無効化・削除処理は「全操作対象への通知」を権限取り消し等の破壊的操作より先に行う。**

## レビュー・検証プロセス

8. **独立レビュワー（Codex CLI・Claude Agent）の判定が食い違うケースが複数回発生**し、必ずコードを直接読んで事実確認する方針を確立した。検証コストが高い＝要件が複雑という兆候でもある。
9. **実際に`npm install`→`build`→`test`を実行し、疑わしい挙動をその場でテストを書いて実証確認する**ことで発見できたバグがあった（C-14：MutationObserverが無関係なDOM変化でツールチップを誤って消す）。動的DOM監視系は検証コストを見込むこと。
10. **設計査読の段階で「当初案が自己矛盾している」ことが判明し設計変更に至ったケースが複数あった**（B-3、C-13）。要件定義の時点で「この状態はいつ・誰が・どう変化させるか」を明示すること。

## 収益化・スコープ

11. **実装は進むがStore提出が進まない。** 実装のしやすさだけでなく「提出までのハードル」（スクリーンショット・説明文・プライバシーポリシー等の準備負担）も踏まえてスコープを検討すること。

# 第2回会合で確定した追加の設計原則

- **Chrome Web Store提出単位のゲート化**：実装完了とStore提出準備完了（権限説明・単一用途説明・プライバシー開示・スクリーンショット・手動テスト票）を別判定にし、次の案へ進む前に少なくとも提出準備まで完成させる運用を導入する。
- **全案共通の仕様テンプレート**：起動契機／manifest権限名／host permission／保存先と保存期間／SW再起動後の復元方法／権限取消時の失敗処理／対応不能なページ・送信経路／外部通信と利用規約確認／MVP受入試験、の9項目を各案の要件定義に含める。
- **リモートコード実行はChrome Web Store審査ポリシー上使えない**ため、辞書・ライブラリは同梱する。
- **`chrome.downloads`に任意のローカルファイル名への事後変更手段（rename等）は存在しない。**
