# 検討テーマ

Chrome拡張機能アイデアのバックログのうち、D〜Hカテゴリ（15案）について、
A〜Cカテゴリ（14案）を実際に実装した経験から得られた教訓を踏まえて要件を
再定義せよ。あわせて、既存29案と重複しない新規15案を提案せよ。

## 背景：これは何の一部か

これは「稟議書_Chrome拡張機能アイデア.md」という29案のアイデアリストの
一部（D〜H、項目15〜29）の見直しである。A〜C（項目1〜14）は既に個人開発者が
実装を終えている。以降のD〜Hおよび新規15案も、同じ個人開発者が同様の体制
（Claude Code + Codex CLIによる並列レビュー、ai-build-councilという
ゲート付き実装ワークフロー）で実装する前提で検討すること。

## 判定基準（統合・裁定で重視する観点）

- 目的適合性：個人開発者が実装可能な規模か
- 制約充足：Manifest V3、Chrome Web Store審査を通せるか
- 根拠の強さ：需要・差別化の裏付け
- リスク：技術リスク・審査リスク・法務リスクが具体的に評価されているか

# A〜Cカテゴリ実装で得られた教訓（14案・全て実装済み）

以下は、A〜Cの14案（項目1〜14）を実際にai-build-councilワークフロー
（独立設計→設計査読→実装→テスト→固定diffの独立実装レビュー→修正→記録）
で実装した際に、実装レビュー（Codex CLI・Claude Agentの並列独立レビュー）
で発見・修正された不具合や、設計査読で修正された論点の一覧である。
D〜Hの再要件定義・新規15案の検討では、同種の問題を事前に回避できる形で
要件・スコープ・Chrome API選定を行うこと。

## 権限設計・審査運用に関する教訓

1. **オリジン単位オプトインアーキテクチャの確立**（C-11〜C-14で採用）：
   常駐content_script・広範なhost_permissionsを使わず、ユーザーが明示的に
   有効化したサイトにのみ`optional_host_permissions`で動的にcontent
   scriptを登録する設計が確立した。サイト単位で動作する拡張機能
   （読みやすさ調整、ツールチップ表示等）はこの設計を標準とすべき。
   広範なhost_permissionsは審査ハードルが上がるため、D〜Hの中でも
   `scripting`＋`activeTab`のみで実装可能な案（ユーザー操作起点）を優先し、
   常時監視系の案は上記オプトイン方式を前提に再設計すること。

2. **Chrome Web Store実際の審査で、manifestの`permissions`ひとつひとつに
   「使用理由」の記入が求められる**（1権限あたり大まかに3点：いつ使うか／
   何のために使うか／それ以外に使わないこと）。権限が広い・多いほど、
   この説明で具体性を出しにくく審査が長引く。要件定義の段階で「本当に
   その権限が必要か」を絞り込んでおくと、後工程が楽になる。

3. **「単一用途（Single Purpose）」の説明を審査で必須提出する。** 1拡張
   機能=1目的で設計しておかないと、この説明で自己矛盾が生じやすい。
   複数機能を持たせたくなる案（例：スニペット挿入＋複数施設共有）は、
   MVPスコープを単一機能に絞ること。

## 非同期・状態管理に関する教訓（繰り返し発生した問題パターン）

4. **TOCTOU競合（検証と実行の間に状態が変わる）が複数の案で独立に発見
   された。** 例：保存判定後・書き込み前にオリジンが無効化されるとレコード
   が復活する（C-11）、タブが合流処理の検証後に別URLへ遷移する（B-8）、
   権限ダイアログ操作中にタブが別オリジンへ遷移する（C-14）。**非同期処理
   をまたいで前提条件を再確認する設計**を、監視・自動処理系の案（F・一部G）
   では最初から要件に含めること。

5. **`chrome.alarms`の一回限りalarmは発火後にChrome側で自動削除される。**
   これを「alarm消失＝再作成すべき異常」と誤認識すると、過去時刻での
   alarm再作成→即再発火→同一内容の二重通知という不具合になる（B-9で発見）。
   通知・タイマー系の案（F・一部D）は、alarm消失が正常系であることを
   要件レベルで明記すること。

6. **Service Worker再起動（MV3の宿命）を前提にした設計が必須。**
   インメモリの追跡状態だけに依存すると再起動で機能停止する
   （B-7で発見・修正）。`chrome.storage.session`（プロセス生存中のみ）と
   `chrome.storage.local`/`sync`（永続）の使い分けを要件段階で明示すること。
   また「`chrome.storage.session`をブラウザ起動時にTTL掃除する」設計は
   自己矛盾（プロセス終了で消える領域を次回起動時に参照できない）になる
   ため、`chrome.alarms`による同一セッション内の周期処理を使うこと
   （C-13で発見・修正）。

7. **無効化・削除処理は「全操作対象への通知」を権限取り消し等の破壊的操作
   より先に行う。** 順序を誤ると通知が届かない（C-11）。

## レビュー・検証プロセスに関する教訓

8. **独立レビュワー（Codex CLI・Claude Agent）の判定が食い違うケースが
   複数回発生し、必ずコードを直接読んで事実確認する方針を確立した。**
   （B-8では「問題なし」という誤判定を、コード確認で覆した）
   検証コストが高い＝要件が複雑という兆候でもあるため、D〜Hの再要件定義
   では「レビューで判定が割れそうな複雑な条件分岐」をできるだけ要件段階
   で単純化すること。

9. **「読んで正しそうに見える」だけでなく、実際に`npm install`→`build`→
   `test`を実行し、疑わしい挙動をその場でテストを書いて実証確認する
   ことで発見できたバグがあった**（C-14：MutationObserverが無関係な
   DOM変化でツールチップを誤って消す不具合）。動的DOM監視系の案
   （F・一部G）は、高頻度でDOMが変化する対象サイト（SNSタイムライン等）
   を要件に含める場合、この検証コストを見込んでおくこと。

10. **設計査読の段階で「当初案が自己矛盾している」ことが判明し設計変更に
    至ったケースが複数あった**（受信箱の自動保存要件矛盾＝B-3、
    storage.session＋起動時TTL矛盾＝C-13）。要件定義の時点で「この状態は
    いつ・誰が・どう変化させるか」を明示すると、こうした矛盾を早期に
    検出しやすい。

## 収益化・スコープに関する教訓

11. A〜Cの実装済み14案は、Chrome Web Store提出まで進めたのは1案のみ
    （ページ情報ワンクリック台帳、審査中）。他は「実装済み・未提出」の
    まま滞留している。D〜H・新規15案の要件定義では、実装のしやすさ
    だけでなく「提出までのハードル」（スクリーンショット・説明文・
    プライバシーポリシー等の準備負担）も踏まえてスコープを検討すること。
