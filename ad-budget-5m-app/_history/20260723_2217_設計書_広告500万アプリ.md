# 設計書（たたき台）: AIプロフィール/証明写真アプリ

`要件定義_広告500万アプリ.md` をもとにした**たたき台**。人間のレビューと
Stage 0のCAC実測を経てから実装に進むこと。数字はすべて未実証の事業仮説。

## 概要

自撮り写真をアップロードすると、AIがスーツ/服装・背景を差し替えた高品質な
プロフィール写真風画像を数枚生成し、単発課金でダウンロードできる消費者向け
Webアプリ（MVP）。用途は就活/SNS/ビジネスプロフィールに限定し、公的書類は
対象外。単位経済が薄いため、サブスク/上位価格でLTVを補強する道筋を持つ。

## アーキテクチャ（案）

- **フロントエンド**: Next.js / TypeScript（スマホファーストのWeb、PWA化は任意）
- **バックエンド/認証/DB**: マネージドなBaaS（例: Supabase / PostgreSQL）
- **画像生成**: 顔を保持したまま服装・背景を差し替える生成
  （既存の画像生成API、またはOSSモデルのホスティング。**自前の基盤モデル
  学習は不要**）。推論原価とレイテンシが単位経済を左右するため要検証。
- **決済**: Stripe Checkout（単発）＋ Billing（サブスク導入時）。カード情報は
  自社保存しない。
- **計測**: 広告CAC/CVR/歩留まりを計測できるよう、流入元・課金・生成完了を
  イベントとして記録（PostHog等）。段階投下の判断に必須。
- **監視**: エラー監視（Sentry等）、生成失敗率の可視化。

## 主要フロー（MVP・一本道）

```
自撮りアップロード
   → スタイル選択（スーツ/背景のテンプレ）
   → AI生成（数枚）
   → プレビュー
   → 単発決済（¥2,480）
   → ダウンロード
```

- 生成は非同期（ジョブ投入→完了通知）。待ち時間と失敗時の再試行を明示。
- 管理画面・複数テンプレ・サブスク基盤・履歴はMVPに含めない（第2フェーズ）。

## データモデル（最小・案）

```
jobs:
  id, user_ref, source_image_ref, style, status(queued/processing/done/failed),
  result_image_refs, created_at
payments:
  id, job_id, amount, currency, provider_ref(Stripe), status, created_at
（顔画像・生成結果は保存/削除方針に従う。個人情報として扱う）
```

## 計測設計（段階投下のため必須）

- イベント: 広告流入（utm）→ アップロード → 生成完了 → 決済完了。
- 集計: チャネル別 CAC・CVR・実粗利、リピート率、（導入後）サブスク転換率。
- 判定: CAC>¥2,500かつ改善見込みなしで停止／LTV>CAC確認で次Stageへ。

## 法規制の実装反映

- 公的書類用途を規約・UI文言で対象外と明記（生成前の同意画面）。
- 景表法：加工の範囲・before/after表示が誤認を招かない文言にする。
- 個人情報：顔画像の利用目的明示・保存/削除・未成年データの扱い。
- 決済情報は外部決済事業者に委ね自社保存しない。

## テスト方針（たたき台）

1. アップロード→生成→プレビュー→決済→ダウンロードの一連フローが成立する。
2. 非対応画像形式・生成失敗・決済失敗の異常系で適切なエラー表示。
3. 公的書類用途への誘導が無く、規約・免責・用途限定の表示があること。
4. 計測イベント（流入/生成完了/決済）が正しく記録されること。
